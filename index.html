課題

常時自動運転

入退社アカウントの発行・停止 自動化

課題
入退社のたびに依頼ベースでアカウントを手作業発行・停止。漏れと遅延のリスクが常にあった。
作ったもの
人事イベントをWebhookで受信し、各種アカウントの発行・停止を自動実行する仕組み。承認フローを設計し、運用マニュアルを整備して承認は業務部門へ引き継いだ。
判断
いきなり全自動にせず、確認運転の期間を挟んで例外パターンを洗い出してから常時自動運転へ移行した。
成果
依頼ベースの手作業 → 人事イベント起点の自動処理。承認操作を業務部門へ移管し、例外時の技術対応を自分が担当する分担にした。
GASWebhookSaaS API
証拠と限界 — 構成・運用期間・例外・移管結果・未計測のもの
人事SaaS（入社・退社・異動イベント）→ Webhook → 受信（GAS）→ 承認シート 承認シート（「承認済み」の行だけを毎時実行／退職者は月次で削除処理） → Google Workspace ／ ビジネスチャット ／ 名刺管理 のアカウント作成・停止・部署変更
運用期間
2026年6月から確認運転（受信したイベントを承認待ちに積むだけで実行しない）。この期間に不要イベントを発見して除外処理を追加し、8月5日に常時自動運転へ切替。
見つけた例外
人事SaaSが毎日同時刻に、実際の異動ではない同一148件の「更新」イベントを送ってくることが確認運転で判明（定期同期バッチ由来）。実異動と区別する処理を入れてから本番化した。本番化後も、1名の退職イベントが日次で17回再送される事象を観測しており、重複の吸収は承認側で行っている。
障害対応
確認運転中に実在社員148件分のイベントが承認待ちへ流入。承認済みの行しか実行しない設計のため実アカウントへの変更は起きず、バックアップを取ったうえで滞留分を除去した。
自分の判断
全自動にせず承認を挟む。誤って退職処理が走ると取り返しがつかないため、人の承認を「実行スイッチ」に置いた。
移管結果
承認操作は業務部門の担当者へ引き継ぎ、手順書を整備。自分は例外時の技術対応のみ。
処理実績
2026年7月23日〜9月1日（約6週間、常時自動運転への切替を含む）: 受信51行、人事SaaS側の再送による重複を除いた実イベント35件。自動完了22件（入社8・異動8・情報変更1・退職5）、手動介入2件（ライセンス上限で保留→座席追加後に再実行、既に手動停止済みだった退職者の台帳整合）、連携エラー2件（入社直後の部署確定イベント）、承認待ち11件（うち8件は会社アカウントを持たない非常勤の退職で台帳更新のみ）。承認シートから集計。

開発スタイル

「AIに書かせる」を、検証と統制で本番品質にする方法。

STYLE 01

AIで作り、責任は自分が持つ

コードはAIエージェントに書かせるが、設計・レビュー・本番検証・運用の責任は自分にある。公開コードでは、AIが入れた安全機構が「報告するが誰も見ない」設計だったのを別モデルの相互レビューで検出し、私が修正方針を4案から選んで差分を確認のうえ採用した。社内ポータルでは、改善案に含まれた既定値が本番で回帰を起こし、原因を特定して環境変数1箇所で暫定復旧した（事前に退けた例ではなく、採用後の障害対応）。非自明な差分は、AIの解説を読む前に自分で読んで言語化してから突き合わせる。

STYLE 02

検証してから「完了」と言う

テスト・コミット前ゲート（秘密情報スキャン等）・AIコードレビューの多段構成。ただし最終の採否判断と実機での動作確認は必ず人間側で行う。

STYLE 03

連携経路はリスクで選ぶ

SaaS連携は公式APIを第一選択とし、提供がない業務は影響範囲・保守性・利用条件を評価してから代替経路を設計する。動けばいい、では作らない。
