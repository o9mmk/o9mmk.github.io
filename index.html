社内ナレッジ検索AI（社内ポータル ＋ AIチャット）

課題
規程・手順書・FAQが散在し、「どこに書いてあるか」の問い合わせが特定の人に集中していた。
作ったもの
社内資料の横断検索・FAQ・AIチャット・全社周知をまとめた社内ポータルを外注せずに構築。AIチャットは社内文書を根拠に、出典つきで回答する。お知らせとFAQは非エンジニアがスプレッドシートを編集するだけで更新できる設計にし、運用を自分に依存させない。
判断
検索は二段構成にした。短い定型のFAQはキーワード検索（BM25）で引き、規程などの長い文書はVertex AIのRAGで引く。文書の種類ごとに、精度と運用費の釣り合う方式を選んだ。
成果
GA4ユーザー数 196人・PV 1,724（2026年8月9日〜9月7日の30日間。グループ他社の利用を含む）。

品質の維持
テスト質問セットで回答の精度を定期的に自動評価している。RAGの検索対象は同期フォルダと突き合わせ、フォルダから消した古い文書を外す処理を同期に組み込んだ（2026年10月の点検で、検索対象104件のうち51件が既に消した文書の残りだったため導入）。
運用期間

障害対応
本番反映後、チャットが聞き返しを繰り返す不具合が起きた。改善案に含まれていた生成設定の既定値が本番にそのまま入ったのが原因で、設定1箇所の変更で復旧し、実画面で直ったことを確認した。検証環境と本番の既定値の違いが根本にあったため、両者を揃えた。発覚まで3日かかったのは、本番反映後の確認を代表的な質問で行っていなかったため。
自分の判断
すべてをRAGに寄せない。FAQは短く言い回しも揃っているためキーワード検索で十分に当たり、運用費も軽い。RAGは長い規程文書に限って使う。二段構成と単一方式の精度・費用の比較評価は未実施。
未計測
問い合わせ件数の減少、担当者の対応時間の変化、維持費と月あたりの保守時間。利用者数は取れているが、業務効果の直接指標はまだ測れていない。
常時自動運転

入退社アカウントの発行・停止 自動化

課題
入退社のたびに依頼ベースでアカウントを手作業発行・停止。漏れと遅延のリスクが常にあった。
作ったもの
人事イベントをWebhookで受信し、各種アカウントの発行・停止を自動実行する仕組み。承認フローを設計し、運用マニュアルを整備して承認は業務部門へ引き継いだ。
判断
いきなり全自動にせず、確認運転の期間を挟んで例外パターンを洗い出してから常時自動運転へ移行した。
成果
依頼ベースの手作業 → 人事イベント起点の自動処理。承認操作を業務部門へ移管し、例外時の技術対応を自分が担当する分担にした。

運用期間
2026年6月から確認運転（受信したイベントを承認待ちに積むだけで実行しない）。この期間に不要イベントを発見して除外処理を追加し、8月5日に常時自動運転へ切替。
見つけた例外
人事SaaSが毎日同時刻に、実際の異動ではない同一148件の「更新」イベントを送ってくることが確認運転で判明（定期同期バッチ由来）。承認済みの行しか実行しない設計のため実アカウントへの変更は起きず、実異動と区別する処理を入れてから本番化した。
自分の判断
全自動にせず承認を挟む。誤って退職処理が走ると取り返しがつかないため、人の承認を「実行スイッチ」に置いた。
移管結果
承認操作は業務部門の担当者へ引き継ぎ、手順書を整備。自分は例外時の技術対応のみ。
処理実績
2026年7月23日〜9月1日（約6週間、常時自動運転への切替を含む）: 重複を除いた実イベント35件のうち22件が自動完了。残りは手動での対応や承認待ち。承認シートから集計。
未検証・未計測
未検証: 自分が不在の期間の通常処理とエスカレーションの実績。未計測: 維持費と月あたりの保守時間。

社内IT基盤とサポート

問い合わせ窓口の再設計

個人チャットへの直接相談で見落としと属人化が起きていた問い合わせ経路を、「施設長 → 相談用グループ → ワークフロー申請」の3段に統一。各拠点のPCに詳しいスタッフも窓口に加えて負担の集中を分散した（現在も全社の標準経路）。

ネットワーク（10拠点）

本社回線の切替を主導し、旧2回線の解約まで完了。10拠点のネットワーク作業は、各拠点の停止可能日時を集めてベンダーと全日程を確定した。ベンダー提案の配線工事（約5万円）は現地調査のうえ自前のLANハブ増設で代替した。

障害対応とデータ保全

旧基幹DBが使えなくなった障害では、影響範囲・法令上の保存義務（5年）・業務継続策・再発防止案を2日で意思決定資料にまとめて経営会議へ提出。市販ツールで開けない旧バックアップを読み取り、5つのDBと添付973件（約908MB）を保全した。

現場の業務シート障害

管理権限のない他拠点所有の業務シートが動かなくなった件で、原因を回答データの肥大（約15万行で関数の処理限界を超過）と特定。所有拠点と上長へ依頼事項を示して約2.4万行へ整理し復旧、月次アーカイブの手順書を付けて現場へ移管した。

全社PC棚卸し

拠点別の未回答台数を示して督促し、回答率を約47% → 約69%へ引き上げた。

開発スタイル

「AIに書かせる」を、検証と統制で本番品質にする方法。

STYLE 01

AIで作り、責任は自分が持つ

コードはAIエージェントに書かせるが、設計・レビュー・本番検証・運用の責任は自分にある。公開コードでは、AIが入れた安全機構が「報告するが誰も見ない」設計だったのを別モデルの相互レビューで検出し、私が修正方針を4案から選んで差分を確認のうえ採用した。社内ポータルでは、改善案に含まれた既定値が本番で回帰を起こし、原因を特定して環境変数1箇所で暫定復旧した。非自明な差分は、AIの解説を読む前に自分で読んで言語化してから突き合わせる。

STYLE 02

検証してから「完了」と言う

テスト・コミット前ゲート（秘密情報スキャン等）・AIコードレビューの多段構成。ただし最終の採否判断と実機での動作確認は必ず人間側で行う。

STYLE 03

連携経路はリスクで選ぶ

SaaS連携は公式APIを第一選択とし、提供がない業務は影響範囲・保守性・利用条件を評価してから代替経路を設計する。動けばいい、では作らない。

ai-orchestrator（orc）

AIエージェントにコードを書かせるためのローカル orchestrator。AIに作業させるときに「やってはいけないこと」を先に機械的に縛る設計です。技術的な詳細は GitHub にあります（Python 3.12、テスト321件、mypy strict）。

  • 代表実装: 出力上限つきの監視ループ、別スレッドのディスク増分監視、exec 後に上限を適用する信頼済みランチャー、上限が効いていない結果を PASS にしない判定（宣言済みのプラットフォーム制約を除く）
  • 設計判断の記録: 最終設計と、同じ要件から案A・案Bを独立に起こし比較評価して決めた過程。保証の範囲と例外は README に明記
  • 相互レビューを使った品質改善の記録: commit 0df91c8（続く ce1c1d4 で監視の抜け道を修正）。AIが入れた修正に「資源上限の未適用を記録しても合否判定に反映しない」「報告を被検査プロセスが改ざんできる」欠陥があり、別モデルのレビューで検出。私は修正方針を4案（記録して判定へ反映／fail-closed で拒否／既知の制約として文書化のみ／公開を後回し）から比較し、未適用を隠さず判定へ反映する案を選択、差分の提示を受けて採否を判断した。実施した検証は321件のテスト・mypy strict・ruff（報告の改ざん耐性、未適用時に PASS しないことを回帰テストで固定）。未検証の範囲は README に明記
